## 2026-08-09 — the last three legacy tools were REMOVED, not shipped deprecated, because they answered wrongly (#505)

**Friction:** #470 planned to ship 2.0 with `find_references` / `get_call_hierarchy` / `analyze_dependencies` still registered as deprecated. Auditing them for the tag showed they are not merely superseded or under-reporting — each answers *confidently and wrongly*, verified by reading the implementations and calling the live tools at `c1a79d5`. `get_call_hierarchy` could never populate `callees` at all (it read module-level names under Jedi's `definitions=True, references=False` defaults, then skipped every result via `if name.is_definition(): continue`) and anchored bare names on the first `_search_all_scopes` match with no ambiguity signal — asking for callers of `analyze_dependencies` returned 9 hits anchored on a local binding in one test file, omitting the real ones. `analyze_dependencies` derived `project_modules` from `rel_path.parts[0]`, which is `"src"` on a src layout, so every first-party module was bucketed as third-party; that emptied the input to the cycle scan, making `circular_dependencies: []` wrong by construction (a real `jedi_analyzer` ↔ `mcp.server` 2-cycle reported as none). `find_references` advertised "ALL usages" with no absence-vs-zero signal. Shipping these contradicts the release's own premise, and the advertised tool description — the only text most MCP clients render — carried the false claim while the deprecation note sat mid-docstring where no client shows it.

**Decision:** Remove all three from the MCP surface **and delete their backing `JediAnalyzer` methods**, so no future wrapper can re-expose them — deprecation was rejected precisely because a registered tool keeps being callable no matter what the prose says. Scope becomes 12 tools removed / 0 deprecated for 2.0. `find_references` gets **no replacement by design**: reverse references stay deferred to #333 and an honest "not available" beats a silently-incomplete list. Removed the superseded `lookup` entry point in the same change (unregistered since the primitives landed, and the only remaining non-MCP consumer of these methods), which forced `get_module_info` out too. Kept deliberately, against the same sweep: `find_importers` (backs the live `imported_by` edge), `find_subclasses`, `find_symbol`, `_search_all_scopes` — each of which *had* carried a `# DEPRECATED … will be removed in the legacy-tool cleanup phase` marker (and a matching docstring) while in fact being load-bearing for `resolve`/`expand`. Since this change **is** that cleanup phase, a later sweep trusting those markers would have deleted live code, so they were rewritten to state what each method backs; no `# DEPRECATED` marker remains in `src/pyeye`. Also kept: `_discover_standalone_files`, which is the only implementation of the `standalone` config contract (the `recursive` / `file_pattern` keys, the default-exclude set, and the skip-files-inside-a-package rule); `get_project_files` scope resolution only unions `self.standalone_paths` wholesale and honours none of it. **Caveat found in review:** that contract is itself currently unreachable — `configure_packages` persists those keys but nothing calls the method, and `exclude_patterns` is never read from config at all — so this retention is provisional on #513, which decides whether to wire it up or drop the surface.

**Anchor:** removed `pyeye.mcp.server.find_references` / `.get_call_hierarchy` / `.analyze_dependencies`, `pyeye.analyzers.jedi_analyzer.JediAnalyzer.{find_references,get_call_hierarchy,analyze_dependencies,get_module_info}`, and modules `pyeye.mcp.lookup` / `pyeye.mcp.lookup_builders`; kept `JediAnalyzer.find_importers`; #505, #470, commit `cc3d85d`. Reverse-reference deferral tracked by #333.

**Verify:** PARTIAL — gold portion: `{t.name for t in await mcp.list_tools()} == {"configure_packages","resolve","resolve_at","inspect","outline","expand","trace"}`; `not hasattr(JediAnalyzer, n)` for each of `find_references`, `get_call_hierarchy`, `analyze_dependencies`, `get_module_info`; `hasattr(JediAnalyzer, "find_importers")`; `importlib.util.find_spec("pyeye.mcp.lookup") is None` and likewise for `pyeye.mcp.lookup_builders`. All covered by `tests/test_mcp_surface_conformance.py`. Separately, `tests/test_scope_defaults_conformance.py` asserts every `SmartScopeResolver.SMART_DEFAULTS` key still names a real `JediAnalyzer` method, which is what let dead keys for these tools survive the methods. PARTIAL residue: "no shipped artifact teaches the removed tools" is only mechanically guarded for the `python-explore` skill (`tests/test_python_explore_skill_conformance.py`, which by design still permits naming them inside the removed-tools warning). Everything else is human review, and the following are **knowingly still stale**, all for the *pre-#505* removals as well: `DOCUMENTATION.md` (documents `find_symbol` / `goto_definition` / `find_references` / `get_call_hierarchy` / `analyze_dependencies` / `find_symbol_multi` as live API), the whole of `docs/api/` (of which only `configure_packages` still exists), `docs/migration-guide.md`, and the metrics/dogfooding docs that use removed tool names as sample telemetry labels (`docs/METRICS_BASELINE.md`, `docs/UNIFIED_METRICS.md`, `docs/DOGFOODING_INTEGRATION.md`, `scripts/claude_hooks/README.md`) — all named in #509's body and covered by its acceptance command. (Review caught that this ledger originally claimed #509 "tracked" them while that issue's body named none of them and its grep covered only `docs/api/` and `docs/migration-guide.md` — so #509 could have closed to its own criteria with `DOCUMENTATION.md` still teaching removed tools. #509 was widened rather than this sentence softened.) Fixed in this change after review caught them: `docs/namespace-packages.md` (documented all four removed tools as live *and* carried a `scope_defaults.methods` block for them — the same defect as the example configs) and `docs/test_coverage_agent_usage.md` (deleted; it documented the agent module removed here). `src/pyeye/agents/` was packaged code emitting `MCPInstruction(tool="mcp__pyeye__find_references", …)` and four other removed names — worse than stale prose, since a consumer following that plan gets tool-not-found — so it was **deleted in this change** rather than deferred (#510), and a new guard (`TestNoPackagedCodeInvokesRemovedTools`) now fails if any packaged module names a removed tool in `mcp__pyeye__*` form. `examples/configurations/*.json` carried `scope_defaults.methods` keys for removed methods and were fixed in this change. A mechanical guard over shipped prose is the obvious follow-up and does not exist yet.

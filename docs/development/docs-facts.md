# Docs built on facts

pyeye's docs state many facts that the code owns: tool names and parameters, edges,
environment variables, entry points, the coverage threshold, the supported Pythons.
Copied by hand, those facts drift. So the docs don't copy them. They name a **fact**,
and `scripts/docs_facts.py` fills it in from the code (#818, #824).

There are two layers:

- **Facts** come from the code and are never edited by hand.
- **Prose** (explanation, ordering, examples) is written by hand and links to facts.

## Using a fact in a page

Wrap the place a fact appears in a named marker block. The block's content is
generated, so you can leave it empty and run `generate`.

Inline, inside a sentence (begin and end on one line):

```markdown
Coverage must stay above <!-- fact:begin ci.coverage_threshold -->85%<!-- fact:end -->.
```

As a block, for tables and lists (the markers on their own lines):

```markdown
<!-- fact:begin edges.table -->
<!-- fact:end -->
```

HTML comments don't render, so on GitHub the page reads normally. Markers inside code
fences or inline code are plain text, which is how this page shows them.

Every fact ID and its current value is listed in `docs/facts/facts.json`. Group IDs,
which render a table or list over several facts (`tool.trace.params`, `tools.core`,
`edges.implemented`, `edges.deferred`, `edges.table`, `ceilings.table`, `env.all`,
`env.deprecated`, `cli.all`), aren't in the snapshot because they have no value of
their own.

For a large table, link to the generated reference page instead of inlining it:
[docs/reference/](../reference/README.md).

## Commands

```bash
uv run python scripts/docs_facts.py generate   # rewrite blocks, reference pages and the snapshot
uv run python scripts/docs_facts.py check      # fail if anything differs from the code
```

Pre-commit runs `generate`. If it changes a file, the commit fails like a formatter
would: stage the result and commit again. CI runs `check` in the `pre-commit` job.

`check` fails when:

- a block's content differs from its fact (the value changed, or someone edited
  inside the block, which is the same failure);
- a block names an unknown fact ID (the fact was removed or renamed);
- a marker is malformed (an unclosed block, a nested one, or an inline block that
  spans lines);
- a reference page or the snapshot is stale;
- a file in the doc registry doesn't exist.

## The doc registry

`src/pyeye/docs_facts/docs.py` lists every documentation file, with its audience
(`human`, `claude` or `both`) and its kind:

| Kind | Meaning |
|---|---|
| `prose` | hand-written explanation |
| `reference` | a page generated by `generate` (`docs/reference/`) |
| `skill` | a skill, or a reference file a skill loads |
| `history` | a record that has to name removed things (changelog, migration guide) |

Every docs check reads this list and nothing else. `tests/test_docs_facts_registry.py`
fails if a Markdown file isn't registered, so **a new `.md` file needs an entry in the
same PR**. The only trees outside the registry are the historical records
(`docs/superpowers/`, `docs/decisions/`, `docs/audits/`) and test fixtures
(`tests/fixtures/`).

## Adding a fact

Facts come from extractors in `src/pyeye/docs_facts/extractors/`, listed once in
`EXTRACTORS` (`src/pyeye/docs_facts/registry.py`). Each extractor owns ID prefixes, so
no two can produce the same fact. To add a family, write an extractor that reads the
code, add it to `EXTRACTORS` and add tests that compare its output with the code read
another way (see `tests/test_docs_facts_extractors.py`). An extractor that can no longer
read its source fails loudly instead of yielding nothing.

# Docs built on facts

pyeye's docs state many facts that the code owns: tool names and parameters, edges,
environment variables, entry points, the coverage threshold, the supported Pythons.
Copied by hand, those facts drift. So the docs don't copy them. They name a **fact**,
and `scripts/docs_facts.py` fills it in from the code (#818, #824).

There are two layers:

- **Facts** come from the code and are never edited by hand.
- **Prose** (explanation, ordering, examples) is written by hand and links to facts.

## Using a fact in a page

Wrap the place a fact appears in a named marker block. The block's content is
generated, so you can leave it empty and run `generate`.

Inline, inside a sentence (begin and end on one line):

```markdown
Coverage must stay above <!-- fact:begin ci.coverage_threshold -->85%<!-- fact:end -->.
```

As a block, for tables and lists (the markers on their own lines):

```markdown
<!-- fact:begin edges.table -->
<!-- fact:end -->
```

HTML comments don't render, so on GitHub the page reads normally. Markers inside code
fences or inline code are plain text, which is how this page shows them.

Every fact ID and its current value is listed in `docs/facts/facts.json`. Group IDs,
which render a table or list over several facts (for example `edges.table`, `env.all`
or `tool.<name>.params`), aren't in the snapshot because they have no value of their
own.

For a large table, link to the generated reference page instead of inlining it:
[docs/reference/](../reference/README.md).

## Commands

```bash
uv run python scripts/docs_facts.py generate   # rewrite blocks, reference pages, snapshot and ledgers
uv run python scripts/docs_facts.py check      # fail if anything differs from the code
uv run python scripts/docs_facts.py changed --base origin/main   # facts this branch changed
```

Pre-commit runs `generate`. If it changes a file, the commit fails like a formatter
would: stage the result and commit again. CI runs `check` in the `pre-commit` job.

`check` fails when:

- a block's content differs from its fact (the value changed, or someone edited
  inside the block, which is the same failure);
- a block names an unknown fact ID (the fact was removed or renamed);
- a marker is malformed (an unclosed block, a nested one, or an inline block that
  spans lines);
- a reference page, the snapshot, `removed.json` or `uncovered.json` is stale;
- a file in the doc registry doesn't exist;
- a live page names a removed name (see below), or a registry entry's `covers`
  names an unknown fact.

## The doc registry

`src/pyeye/docs_facts/docs.py` lists every documentation file, with its audience
(`human`, `claude` or `both`) and its kind:

| Kind | Meaning |
|---|---|
| `prose` | hand-written explanation |
| `reference` | a page generated by `generate` (`docs/reference/`) |
| `skill` | a skill, or a reference file a skill loads |
| `history` | a record that has to name removed things (changelog, migration guide) |
| `record` | a measurement record: its front matter gives the `date`, `command` and `commit`, and a line that links it may state the number it measured (D12) |

Every docs check reads this list and nothing else. `tests/test_docs_facts_registry.py`
fails if a Markdown file isn't registered, so **a new `.md` file needs an entry in the
same PR**. The only trees outside the registry are the historical records
(`docs/superpowers/`, `docs/decisions/`, `docs/audits/`) and test fixtures
(`tests/fixtures/`).

## Executed examples

A tool example in `docs/api/`, `docs/reference/`, a skill, or any prose page for
humans (audience `human` or `both`, outside `.claude/`) can be **executed**
instead of trusted (#828). Tag the fenced block, and give the call's arguments as a
JSON object. Leave out `project_path`; the runner supplies it:

````markdown
```json pyeye-example tool=inspect
{"handle": "myapp.config.Settings"}
```

```json pyeye-output
{"found": true, "kind": "class", "edge_counts": {"members": 3, "superclasses": 1},
 "…": "<omitted>"}
```
````

An example whose result depends on earlier calls (state that accumulates over a
session, #953) gives a JSON **array** of argument objects instead: the runner
calls the tool with each in order, on the same project, and a shown output
matches the last call's response.

The `json pyeye-output` block is optional. It must come straight after its example,
with only blank lines between them. `fixture=<name>` runs the example against
`tests/fixtures/<name>/` instead of the default, `tests/fixtures/docs_examples/` (a
small `myapp` package).

`tests/test_docs_examples.py` calls each example through the MCP server. It checks a
primitive's response with the conformance linter, and matches a shown output on
**structure**, not values (design C10):

| In a shown output | Means | Fails when |
|---|---|---|
| a key | the response has it, with the same JSON kind | it's missing or a different kind |
| `"…": "<omitted>"` | this level leaves keys out | it's missing while keys are left out, or present when none are |
| `"<omitted>"` as the last array item | items are left out | it's missing while items are left out, or present when none are |
| `"k": "<absent>"` | the response does **not** have `k` | the response has `k` |
| `found`, `kind`, `reason`, `ambiguous` | compared by value | the value differs |

A reader must never take a trimmed example for the whole response, so every trim is
marked. `check` also fails on a malformed tag (anything mentioning `pyeye-` that
doesn't fit), an output block with no example straight before it, a body that isn't
JSON, and an example anywhere else: a `history` page (it records the past, which may
no longer run), Claude-only prose, or a page under `.claude/` other than a skill.
Untagged blocks are prose.

## Removed names

A fact that disappears from the code can't fail a block once nothing binds it, but
prose can still name it. So `generate` records every removal in
`docs/facts/removed.json`: when a tool, parameter, env var, entry point or edge leaves
the snapshot, it's appended with `"removed_in": "unreleased"`, and
`scripts/changelog.py prepare` writes the release over it. Entries are never deleted.
The file also holds the names removed before the registry existed (the v1 tools).

Each entry's `match` says how prose is scanned for it, and it's the only field to edit
by hand:

| `match` | Fails on | Default for |
|---|---|---|
| `word` | any mention | tools, env vars, entry points |
| `heading` | only an API heading (`## name`), for a name that lives on as an internal method | set by hand |
| `code` | only a mention in inline code (`` `callers` ``) | edges, whose names are common words |
| `none` | nothing: recorded, not scanned | parameters (runnable examples catch those, #828) |

On a `prose` or `skill` page, a line that names a removed name passes only if it also
says "removed", and each such mention must also be in the page's allow-list in the
registry, `allow={"removed-name": (...)}`, by its exact message (for example
`names removed tool '<name>' beside 'removed'`). The list only shrinks: a new
mention fails until it's added on purpose in the diff, and an allowance whose mention
is gone fails until it's deleted. Messages carry no line numbers, so editing elsewhere
on the page doesn't disturb them, and one allowance covers exactly one mention. From the next major release after an
entry's `removed_in` (the newest release in `CHANGELOG.md`), even a marked line fails:
only `history` pages may name it then. `history` and `reference` pages aren't scanned.

## Uncovered facts

A fact is covered when a `prose` or `skill` page explains it: the page shows it in a
marker block, or its registry entry lists it in `covers` (a group ID stands for its
members). A link to `docs/reference/` doesn't count, since those pages list every fact.

`generate` writes every uncovered fact to `docs/facts/uncovered.json`. The `baseline`
section holds the facts that were uncovered when the ledger was created; it's triaged
once (#831) and only shrinks. Facts uncovered after that are listed under `new` with
`first_seen`, the release they first appeared in. The ledger never fails a check: a new
entry shows up in the PR diff, for the reviewer and for `/docs-review`. An entry leaves
when its fact is covered or no longer exists.

Some fact families are reference data rather than claims a page should explain, such
as the list of pre-commit hooks. A setup declares those families **reference-only**:
their facts never enter the ledger, and `generate` and `check` print a note naming them
(#1108). The facts still bind into pages and still show in the snapshot and the
changed-fact list.

A large family can also keep its **own snapshot file**, so `facts.json` diffs stay
readable. Its facts move out of `facts.json` into that file. The removed-name record
and the changed-fact list read every snapshot file together, so moving a family to its
own file removes nothing.

## Changed facts

`changed --base <rev>` diffs the snapshot against the one at `<rev>` and lists the facts
added, changed and removed, with the pages that bind each one. CI writes it to the
`pre-commit` job's summary on pull requests. It never fails: it's the scope of a
change-triggered `/docs-review`.

A group ID (a view) that gained a member is listed too, under "Views with a new member",
with the pages that bind it. A new member counts as covered as soon as it exists, so this
is what sends those pages to review (#1108).

## Adding a fact

Facts come from extractors in `src/pyeye/docs_facts/extractors/`, listed once in
`EXTRACTORS` (`src/pyeye/docs_facts/registry.py`). Each extractor owns ID prefixes, so
no two can produce the same fact. To add a family, write an extractor that reads the
code, add it to `EXTRACTORS` and add tests that compare its output with the code read
another way (see `tests/test_docs_facts_extractors.py`). An extractor that can no longer
read its source fails loudly instead of yielding nothing.

## Running it on another repository

`scripts/docs_facts.py --root <repo>` runs on any Python repository that declares
what to check in `[tool.pyeye.docs_facts]` in its `pyproject.toml`, or under
`"docs_facts"` in its `.pyeye.json` (which wins). Only the repository's own files are
read for this config, never the user's global pyeye config. A repository with neither
has nothing to check, and the command says so (#1091).

The config is data only. docs-facts never imports or runs the analysed repository's
code: facts come from kinds built into pyeye, which read files.

```toml
[tool.pyeye.docs_facts]
changelog = "CHANGELOG.md"        # optional: read for the current release

[[tool.pyeye.docs_facts.facts]]
id = "settings.concurrent_requests"
from = "literal"                  # a module-level constant, folded from the source
file = "app/settings.py"
name = "CONCURRENT_REQUESTS"

[[tool.pyeye.docs_facts.facts]]
id = "project.requires_python"
from = "toml"                     # or "json" / "yaml": a dotted key path
file = "pyproject.toml"
key = "project.requires-python"

[[tool.pyeye.docs_facts.docs]]
path = "docs/architecture.md"
audience = "human"                # human, claude or both
kind = "prose"                    # how the checks treat the page
```

- **`facts`** reads a value from a file. `literal` folds a Python constant
  (literals, names bound in the same file, f-strings and set or string operators);
  it never follows the file's imports. `toml`, `json` and `yaml` read a dotted key
  path; YAML is read with `yaml.safe_load` only. A fact's ID is `prefix.name`.
- **`extractors`** names other built-in kinds with their options:
  `[[tool.pyeye.docs_facts.extractors]]`, with `kind = "<name>"` and the kind's
  options.
- **`docs`** is the doc registry, written as tables. **`rules`** is `"all"` (the
  default) or a list of rule IDs. A rule whose facts the repository doesn't have,
  such as pyeye's own edge rules, is skipped and reported, never run.
- **`paths`** moves the records (`snapshot`, `removed`, `uncovered`,
  `review_state`) from their default `docs/facts/` files. Its `snapshots` table gives a
  fact family its own snapshot file: `[tool.pyeye.docs_facts.paths.snapshots]` with
  `arch = "docs/facts/arch.json"`.
- **`reference_only`** lists the fact families kept out of the uncovered-fact ledger,
  e.g. `reference_only = ["arch"]`.

Anything that names code to import, such as a `package.module:attr` value, is
refused, as are unknown keys, kinds and rules, and files outside the repository.

## The docs site

The same Markdown is published to [GitHub Pages](https://okeefeco.github.io/pyeye-mcp/)
with MkDocs and the Material theme. Nothing on the site is written separately:

- **What's published** comes from the doc registry (`src/pyeye/docs_facts/site.py`):
  pages for human readers, plus the generated reference pages. Skills and Claude's
  instructions stay off. A history page waits until its honest-claims seeds are gone.
  An entry's `site=True` or `site=False` overrides the rule (the PR template and
  `changes/` are `site=False`).
- **The nav** is built from the same list by `scripts/mkdocs_hooks.py`. `mkdocs.yml`
  lists no pages, so a page reaches the site only by being registered.
- **Paths are repo paths:** `README.md` is the home page and `docs/api/README.md` is
  `/docs/api/`. A relative link works the same on GitHub and on the site. A link to a
  repo file the site doesn't publish points at that file on GitHub.

CI builds the site with `mkdocs build --strict` in the `pre-commit` job, so a broken link
fails the PR, and deploys it on every push to `main`. To preview it locally:

```bash
uv sync --frozen --group docs
uv run --frozen --group docs mkdocs serve
```
